§0 · 执行摘要

2026 年的 PostgreSQL 系后端选型没有通吃赢家

五个方案形态、六个维度、等权合计：开源组合栈 25 分居首，InsForge 21 分次之，Supabase 两版并列 19 分，Nubase 14 分垫底——但这个排序是价值观的产物，换一组权重即翻转。

本报告以 2026-08-16 核查的事实为底座，对 Supabase 托管版、Supabase 自托管版、InsForge、Nubase 与开源组合栈，按开发便利性 / PG 原生度 / 可扩展性 / 模块不锁定 / 私有云可转化度 / 周边生态六个维度逐一打分。所有打分都能回溯到第二章方案卡中的具体事实——版本号、容器数、许可证、stars、事件——不接受「感觉分」。

三个核心判断

  • 判断一：Supabase 仍是基准，但正被两面夹击。生态优势在 2026 年依然断层第一；但向上，20+ 计量项（磁盘 $0.125/GB、出口 $0.09/GB、PITR $100/月 add-on）使成本随规模线性恶化；向下，PG17 镜像弃用 TimescaleDB 事件证明扩展决策权在平台而不在用户——「用的是真 PG」与「PG 归你管」是两回事。
  • 判断二：2026 年的分化轴是「Agent 操作面」。BaaS 功能面已高度同质化，新竞争点是谁把后端变成 AI 编码代理可直接操作的对象。InsForge 的 MCP 语义层、CLI JSON 输出、backend branching 与 diagnose 自愈是当前五方案中最完整的 agent DX（12,757 stars、日更提交）。
  • 判断三：PG 扩展生态使「一个库干五件事」在中等规模成立。pgvector + pg_search 0.25.2 + TimescaleDB 2.29.1 + pgai + DuckDB 的组合，让 OLTP、全文搜索、向量检索、时序、分析五类负载在 TB 以内收敛到一个 PG 底座；代价是 AGPL-3.0 与 TSL 两条许可证硬约束。

SQLite 是「我的记忆」，PG 是「我们的事实」——混淆两者是最常见的架构错误。

— 本报告 · 第六章，2026-08-16

语境端侧（SQLite local-first 记忆）与中枢（PG 系统记录）的双层分工模型。 为何重要第一章的选型结论天然兼容未来的 local-first 扩展，不存在「选了 PG 底座就锁死端侧路线」的问题。

行动建议。① 先按权重自检明确价值取向，再查表选型；② 任何规模都不要选 Nubase 上生产，Supabase 自托管不要当中小 SaaS 主力；③ 采用 InsForge 自托管前务必显式设置 ENCRYPTION_KEY（密钥回退链 #905/#1552 未闭合）；④ 采购含 pg_search（AGPL）或 TimescaleDB 高级功能（TSL）的栈前，先过法务。

§1 · 五大方案逐卡

五张方案卡，一个无锁定参照系

全报告的事实底座：一句话定位、架构组件、关键事实、优势、劣势与成熟度判定——所有数字均来自 2026-08-16 的核查调研，厂商自测数据已标注。

Supabase

托管基准 · 生产级

PostgreSQL 托管后端的事实标准，所有「PG 系 AI 原生后端」都在对标它。Pro $25/月/组织，生态最厚。

核心组件多年未变：Postgres、Auth（GoTrue）、PostgREST、Realtime、Storage、Studio、Kong、Supavisor。风险：自托管是 community-supported 而非官方 SLA；PG17 镜像不再内置 TimescaleDB；20+ 计量项使成本与「纯 Postgres」不可直接对比。

InsForge

Agent 原生 · 成长早期

YC（P26）支持的 Apache-2.0「agent-native」BaaS：MCP 语义层 + CLI 控制面，自托管最小栈仅 3 个核心容器。

12,757 stars / 1,138 forks（2026-08-14 GitHub API 实测），最新 v1.5.6，PG15 + PostgREST v12.2.12。风险：密钥回退链 #905/#1552 未闭合——自托管务必显式设置 ENCRYPTION_KEY；MCPMark 基准为厂商自测未独立复现。

悬停查看完整事实

Nubase

真实但稚嫩 · 不宜生产

2026-06-08 才开源的 AI 原生自托管后端，八大模块一镜像打包；mem0 风格 Memory + AI Gateway 是五方案中唯一内置的。

约 620 stars 但 GitHub Issues 为 0、仅 5 PR——社区互动与 star 数异常不匹配；无公司信息、无定价页、无 Realtime/备份/HA/SSO。v0.1.4 + 两个月历史，仅作技术观察对象。

悬停查看完整事实

ParadeDB

PG 发行版 · 不是 BaaS

把 BM25 全文/混合搜索做进 PostgreSQL 的发行版：pg_search 0.25.2 + pgvector 一镜像，省掉 Elasticsearch 同步管道。

AGPL-3.0 网络条款义务，商业采购需法务确认；须配置 shared_preload_libraries 并重启；AWS RDS 不支持、Neon 已对新项目禁用——实质上是「自管 PG 专属」。YC S23，Series A1 $12M（2025-04）。

悬停查看完整事实

TimescaleDB

时序老将 · Tiger Data

PG 时序/连续聚合扩展的老牌厂商：hypertable 自动分区、连续聚合做 K 线、Hypercore 列式压缩；2.29.1 起仅支持 PG 16/17/18。

许可证双轨：Apache-2.0 核心版 + TSL 高级功能（自用免费、禁止托管转售）。timescaledb-ha 镜像内置 pgvector/pgvectorscale/pgai。Supabase PG17 已弃用 TimescaleDB——托管生态位在收缩。

悬停查看完整事实

组合栈

零锁定参照系 · 唯一已落地 LPK

用可独立替换的开源组件自行拼装 BaaS：ParadeDB + PostgREST + Authentik + MinIO + Mercure + Traefik。

常驻内存 4–6 GB，一台 4C8G VPS（约 €22/月）承载 1–10 万日活；已提供懒猫私有云 LPK 打包与一键部署脚本，是五方案中唯一直接面向私有云落地的路径。代价：运维自担，无统一控制台。

§2 · 六维评分矩阵

每一格分数，都能回溯到一条事实

1–5 分整数刻度，5 = 该维度五方案中最强，1 = 存在硬缺陷；每格附一句判词，判词必须能回溯到方案卡中的具体事实。评分是「加权假设下的相对位置」，不是绝对质量判定。

等权假设下总分为：组合栈 25 > InsForge 21 > Supabase 托管 19 = Supabase 自托管 19 > Nubase 14。这个排序本身是「不锁定与私有云各占六分之一权重」这一价值观的产物，换权重即翻转：维度①权重约 >30% 时托管版胜出；维度④+⑤ 合计权重约 >35% 时组合栈胜出且不可撼动。

误用警告。① 本表是 2026-08-16 时点的快照，InsForge（日更提交）与 Nubase（v0.1.x）的分数半衰期可能只有数月；② 维度⑤的 5 分依赖本项目自建的 LPK 参照实现，换其他私有云目标时结论方向不变、分数需重估；③ 合计分不应被引用为「某方案比某方案好 20%」这类线性陈述——维度间不可通约，正确用法是先定权重再看排序。

§3 · 规模分层技术采用

日活一万以下求快，一到十万是战场，十万以上收回自管

逐层回答同一个问题：在这个规模下，选什么、备选什么、明确不要选什么。1万–10万区间是三条路线分岔的真正战场。

Tier 1（<1万 DAU）推荐 Supabase Free 起步，次选 InsForge 自托管（3 容器）或 PocketBase；不要在这一层自建 K8s 或引入任何按席位计费的企业组件。Tier 2（1万–10万）无普适最优解，按「成本 / 控制力 / 运维负担」三轴选边：求省心选 Supabase Pro，求 agent 工作流选 InsForge Pro，求成本确定性与零锁定选 €22/月自管组合栈。Tier 3（>10万）BaaS 平台整体退场，正确形态是「自管 PG + Citus + Keycloak/Cerbos + K8s/Terraform」，同时 AGPL 与 TSL 许可证从纸面条款变成真实的采购约束。

升级触发条件（出现这些信号就该往下一层迁）

  • T1→T2：Supabase Free 额度触顶（MAU/磁盘连续两周 >80%）；出现第一个付费客户需要 PITR 与备份 SLA；团队从 1 人扩到 3 人以上。
  • T2→T3：Supabase 月度计量账单超过自管成本的 2 倍；合规方首次要求 SOC2 自证或数据驻留；单库写入成为瓶颈需 Citus 分片；RLS 已无法表达权限模型。
  • 反向信号：若自管栈的运维投入超过一名工程师 30% 工时，应考虑反向迁回托管——分层是双向的。

§4 · 应用类型解决方案

四类负载，四条「最小可行栈 + 升级路径」

CRUD、Search、Data-intensive、金融交易——同一套栈在四类负载下的优劣会反转。共同主线：默认从「PG + 扩展」出发，只在量化触发条件命中时引入专用引擎。

CRUD 类的瓶颈不在数据库，而在「API 的边际生产成本」——PostgREST/Hasura 做到「建表即 API」，RLS 直接成为安全边界。Search 类走三级阶梯：tsvector + GIN 起步，百万行内别上 ES；BM25/混合搜索上 pg_search 0.25.2（先过 AGPL 法务关，且实质是自管 PG 专属）；百亿级文档或跨地域分片才上 ES/ClickHouse + CDC。Data-intensive 类用 ParadeDB 一镜像起步，DuckDB 做嵌入式 OLAP，pgai 把 embedding 管道消进数据库。金融交易类的正确答案不是「选一个最快的库」，而是 PG 系三层组合。

§5 · SQLite Local Memory × PostgreSQL

不是二选一，而是「端侧真相源 × 中枢系统记录」的双层架构

SQLite 赢在它天然是端侧的唯一选项（零部署、离线、隐私），PG 赢在它天然是中枢的唯一选项（多租户、审计、共享）。记忆逻辑随规模逐层下沉，API 形状全程不变。

分工的第一性原理是「数据的物理归属」：随人/随设备走的数据放 SQLite，随组织/随系统走的数据放 PG。memweave 参考实现（FTS5 + 向量混合搜索、时间衰减、MMR、WAL 多 Agent 并发、Markdown 真相源，pytest 7/7 通过）把这条边界落实为工程事实。 同步路径按可实现性排序：应用层批量 UPSERT（今天就能做）→ DuckDB 联邦查询胶水（本周就能做）→ PG FDW/逻辑复制（长期方向，谨慎评估）。

三点补充判断：① 阶段二是最容易被跳过也最值得停留的阶段——多数团队的「共享记忆」需求用 UPSERT + PostgREST 就能满足，不必过早引入 CRDT 或 FDW。② 阶段三不等于抛弃 SQLite：SQLite 从「真相源」降级为「缓存+缓冲」是健康的架构退位而非失败。③ 三阶段的 API 形状（write_memory / search）全程不变——演进改的是数据位置，不是调用方代码。

采用前验证清单

以下六项按执行顺序排列，任何方案（含托管版）在进入生产前都应打勾；Nubase 等稚嫩项目须全部通过且结果留档，成熟托管服务至少完成 3–6 项。
